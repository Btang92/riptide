# Daily research run: guide

Goal: find changes that make RIPTIDE more profitable after Kalshi fees, prove them on rounds the model has not seen, and propose them. Never make a change live; Brandon approves in the app.

## Each run
1. `node lab/pull.mjs` (env: RIPTIDE_SERVER, RIPTIDE_KEY). Read `lab/data/research.json` → `notebook` (what earlier runs tried and learned) and `ver` (the live version; if it is null, the live version is the bundled one, which matches the oldest folder in `v/`).
2. Run the loss autopsy: `node lab/autopsy.mjs lab/data`. It splits every settled call by confidence, price paid, edge, hour, distance, momentum, volatility, regime and how the read moved after the call, and marks groups that win or lose significantly more than average. Put a short "Loss autopsy" paragraph in the report (biggest loss drivers, with n and ¢/contract), track how the groups change day to day in the notebook, and use it to choose ideas.
   Standing finding (Oct 22, 249 calls): ~43% of losses still looked right at every check through 10:00 and flipped in the last 5 minutes; ~57% had already turned against the call by 3:00–5:00. Ideas aimed at each: an early-warning exit or a confirmation rule for the first group's opposite (turned early), and a late exit / sell-at-bid rule for late flips (test with checkpoint prices).
   Bigger samples: `lab/data/khist.json` holds every imported Kalshi round (official strike, result, and YES/NO asks at 2:00–10:00). Market-price ideas can be tested on all of it. If `api.exchange.coinbase.com` is reachable from your session, download 1-minute BTC candles for the same period and rebuild RIPTIDE's model probability for each round (copy the feature/probability code from the live `v/<ver>/index.html`), so model ideas can be tested on thousands of rounds instead of only RIPTIDE's own calls. If it isn't reachable, say so once in the notebook and continue with what you have.
   Replay kit (from the repo root): `node lab/replay/extract.mjs <live ver>` (copies the model code), `node lab/replay/candles.mjs` (Coinbase 1-min candles → lab/data/candles.json), `node lab/replay/build.mjs` (features + raw prob at every checkpoint for every round → lab/data/rounds.json), then `lab/replay/sim.mjs` (live brain selection, live bet rule, exits, paired comparisons; see test-*.mjs for examples).
   Missed chances (Oct 23, 337 calls): skipped rounds where a later check (3:00–8:00) showed value went 115–62, about +3.8¢/contract after fees (noise roughly ±3.4¢). Test a "second-chance entry" properly: after a skip, keep checking and bet the first checkpoint that clears the bet rule, with an 8:00 cutoff. Also test the trading-hours window (live is 12–24 ET; 04–08 ET has looked strong) and whether 8:30/9:30/10:00 ET news-time rounds need their own handling (sudden breakouts).
   Queued by Brandon (Oct 23): test two new input families, each on its own and added to the current brain inputs:
   - Market structure (`lab/structure.mjs`): swing highs/lows labelled HH/HL/LH/LL from 1-minute (and 5-minute) candles before the call, giving trend structure, break of structure, and where the strike sits versus the last swing high/low. Uses Coinbase candles, so it can be tested on the full Kalshi history.
   - Buy/sell pressure (`lab/flow.mjs`): per-minute aggressive buy vs sell BTC volume from Coinbase trades (e.g. last 3/5/15 minutes' buy share, and its change). Every run: `node lab/flow.mjs 30 20` first (about 20 minutes, extends the stored history; the data grows a few days per run), then commit and push `lab/flowdata/minutes.json` so the next run continues from it. Test on whatever span is stored so far and say how many rounds that covered.
   An input "helps" only if it improves log-loss and ¢/contract after fees on unseen rounds by more than the noise. If one wins, adding it to the live brain needs server code (the 24/7 server computes the inputs), so the proposal must say needsServer: true and describe exactly what the server must compute.
   Key finding (Oct 23): RIPTIDE's lean matched Kalshi's favourite in 65 of 69 rounds today (40 of 43 right leans, 25 of 26 wrong ones). At call time it adds almost nothing the price doesn't already know, and its price filters are not what's losing rounds (value bets blocked by the price band were −0.5¢/ct, by trading hours −8.4¢/ct). So priority is NEW information Kalshi hasn't priced yet: buy/sell pressure, market structure, and Kalshi lag (the BTC composite moved over the last 1–3 minutes but the Kalshi ask hasn't caught up; test with checkpoint px vs ya/na changes, and say if minute data is too coarse).
   Chat findings (Oct 23 evening): (a) Buy/sell pressure at the call, first look on 104 rounds: no signal (last 3/5/15-min buy share right 57/48/47%, RIPTIDE 66%; RIPTIDE equally right whether flow agreed or not). Keep growing the flow data and retest on 500+ rounds before ruling it out, and try sharper forms (big-trade imbalance, flow vs price divergence). (b) A locked read at any minute 2:00–10:00 is right about as often as Kalshi's favourite at that minute (67%→79%), and the price rises in step, so ¢/contract stays near zero (+2.4 at 2:00, −3.7 at 10:00). Edge has to come from information the market hasn't priced, not from waiting.
   Queued Oct 23 (settlement + timeframe checklist):
   - 60-second settlement average: Kalshi settles on the BRTI average over the final 60 seconds, but RIPTIDE's P(up) uses spot with the full time left. Test the averaging-aware version (variance of a 60-second average ≈ one third of 60 seconds of variance, so effective time ≈ seconds left − 40 when more than a minute remains) on calibration and ¢/contract, at 2:00 and at later checkpoints.
   - Indicator timeframe: RIPTIDE's RSI/MACD/EMA/patterns come from 1-minute candles. Test the same inputs on 5-minute and 15-minute candles (and RSI overbought/oversold as a reversal flag) to see whether the slower chart adds information.
   - Early exit / cut loss: test selling at the bid when the read turns against the call at a checkpoint (the ~57% "turned early" losses), versus holding, using checkpoint YES/NO prices with a 1–2¢ spread allowance.
   Settled Oct 24 (lab/hourstudy.mjs, 3,163 rounds): end-of-hour rounds (:45–:00) do NOT flip more. Favourite at 10:00 lost 17.8% / 19.4% / 16.8% / 18.3% for the :00/:15/:30/:45 rounds; the :45 round's last 5 minutes are the calmest of the hour (median move $31 vs $36; minutes :55–:59 run 0.80–0.88× normal).    Settled Oct 25 (lab/lastminute/, 751 rounds, 4.5M Kalshi trades): in the final 45 seconds Kalshi's last trade predicts settlement far better than settlement-average math built from free per-second prices (log-loss 0.010–0.040 vs 0.073–0.153), and the math's 2¢+ "edges" lost 0.4–3.7¢/contract.    Settled Oct 27 (lab/disagree.mjs, 2,848 rounds, raw model rebuilt from Coinbase candles): when RIPTIDE's read takes the side Kalshi prices under 50¢, the market wins: at 2:00 that side won 38.8% at 47¢ (−9.9¢/ct ±4.8), at 5:00 43.1% (−5.6¢/ct). Re-run monthly as data accumulates (needs 1,000+ rounds with 5¢+ gaps to settle).
   Oct 28 (lab/maker/, 220 rounds, every Kalshi trade 1:30–9:30): resting bids 1–8¢ under the last trade, re-posted each minute on both sides, lose to adverse selection: strict fills −1.3 to −2.9¢ per filled contract (±1–2.5), optimistic fills −0.1 to −1.8¢. Filled bids win only 41–50%. Re-centring on Kalshi's own last trade can't avoid being picked off; a working maker needs a fair value that leads Kalshi (sub-second BTC from the BRTI exchanges) and quotes that move within a second, i.e. a fast server with live feeds. Not viable at RIPTIDE's once-a-minute speed.
   Nov 1 (lab/trendhour.mjs, 3,973 rounds, read at 4:00): trends (BTC's 60-min move > 1 normal swing) occur in ~26% of rounds and carry on (round finishes with the trend 59% up / 63% down) but are priced in (buying the favourite −1.3 to −1.6¢). 3. Pick 1–3 ideas not yet settled in the notebook. Prefer ideas that change *price paid* or *which rounds to bet*, since entry price drives most of the profit.
   Backlog: limit (maker) entries a few cents under the ask; Kalshi-lag (BTC moved, Kalshi price hasn't yet); previous round's result; edge-size buckets; price-band limits; hour/weekday effects; waiting rules; new candle/indicator features; recency weighting; risk limits (daily loss cap, streak pause).
4. Test walk-forward: fit on older rounds, score on the newest ~25%. Use the same bet rule as live (prob ≥ ask + fee + margin; fee = 0.07·P·(1−P) per contract). Report ¢/contract after fees, bets, win rate, and the noise (±1 standard error). An idea "wins" only if it beats the live model by more than its noise and has 150+ test bets.
5. If an idea wins: copy `v/<live>/index.html` to `v/<new id>/index.html` (id = YYYY-MM-DD plus a letter), make the smallest change that implements it, set `const APP_VER` to the new id, check the script parses (`node -e` with `new Function`), commit and push to `main`. Do not touch other versions.
   If the change needs new server code (riptide-server.gs), say so in the proposal (`needsServer: true`); do not try to change the server.
6. File the report with `node lab/post.mjs report.json notebook.json` (use `-` in place of report.json to save only the notebook). The lab scripts retry on their own; Google's server is slow or flaky now and then, and a full download can take a few minutes.
   Do not file a report whose proposal points at a version you didn't push today; the latest report replaces any earlier proposal in the app.
   Exception: until the live version is 2026-11-12a or newer, a report with no proposal of its own carries `{ ver: "2026-11-12a", title: "Day Trade desk", detail: "Stock day-trading desk: gappers + news, VWAP/opening range/key levels, share sizing, daily loss lock, journal. Paste the new server code and add ALPACA_KEY and ALPACA_SECRET in Script Properties first.", needsServer: true }`.
   - report: `{ at, title, summary (one line), text (plain-language paragraph), tests: [{ name, result, win }], proposal: { ver, title, detail, needsServer } | null }`
   - notebook: `{ at, entries: [...] }`. Keep everything still useful from the previous notebook, add today's results, and keep it under ~40 KB.
7. Keep the report plain and honest. If nothing beat the live model, say so; no proposal that day is a normal result.

## Rules
- The research key can only file reports and notebooks. It cannot change settings, the live version, or the password, so don't attempt it.
- No real-money actions, no Kalshi keys, nothing outside this repository and the server.
- Never mention other bots or where RIPTIDE's original model came from.
